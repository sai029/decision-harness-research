---
指揮はメインスレッドが行う（サブエージェントは入れ子にできない）。状態はファイルに残す。

## 開始前
- `docs/plan.md` が人間に承認されているか確認する。未承認なら止めて確認する
- `work/rounds/` の最新ラウンド番号を数え、N を決める（最大4）
- 次ラウンドを始める前にコスト見込み（並列5＋E）を人間に一言伝える

## Phase 1（N=1、または再調査対象のみ）
researcher-a/b/c/d/f を**同じ応答で並列に**起動する。各々に渡す: ラウンド番号、出力先 `work/rounds/round-N/<id>.md`。N≥2 は前ラウンドの自分の出力パスと、E の該当指摘の**原文**。

## Phase 2
critic-e を起動し `work/rounds/round-N/E-review.md` を書かせる。A〜D, F の出力パスだけを渡し、あなたの解釈や要約は渡さない。

## Phase 3
E の指摘のうち「再調査要／設計変更要」に関係する担当だけを再起動（Phase 1 と同様、指摘原文を渡す）。軽微は最終ドキュメントで直す。

## Phase 4: 飽和判定
`work/rounds/round-N/summary.md` に次の表を書く。判断は表の数値で行い、感覚で「十分」としない。
| 項目 | N-1 | N |
| E の「新規主要候補」件数 | | |
| うち設計を変えた採用件数 | | |
| 未解決の「再調査要／設計変更要」 | | |
| 出典の一次確認率 | | |
- 採用0件が2ラウンド連続、かつ未解決0 → 終了条件2を満たす見込み。Phase 5 へ
- 満たさず N<4 → Phase 2 に戻る
- N=4 で未満足 → 未飽和と明記して人間に判断を仰ぐ（延長・打ち切り・絞り込み）

## Phase 5: 確定
- 終了条件 3（DDL を SQLite で実行、プロンプトを合成データで試行）の証拠ファイルが `work/` にあるか確認する。無ければ作る側（C, B）に実行させる
- `docs/research/00〜05, 99` を書く。`99` に指摘と対応の表、飽和判定の表、試した検索クエリ、出典の一次確認率を載せる
- 書いた本人（メイン）が自己申告で完了としない。critic-e に最終版の確認レビューを1回依頼し、結果を `99` に反映してから、人間に承認を求める

## 守ること
- E の指摘文を担当に渡す時、弱めたり要約したりしない
- 実データ・秘密情報は扱わない。例は合成データ
