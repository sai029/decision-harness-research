# 調査計画（改良版）

状態: 草案（人間の承認待ち）

## 目的
人間（本人・先輩・上司）の判断基準・思考過程・前提を記録し、必要な時に AI へ注入することで、0→1タスクを「人間の判断待ち」なしで完遂させる構成を確立する。
コア仮説: 自律作業の最大のブロッカーは人間の判断であり、判断の記録と JIT 注入でそれを減らせる。

## 元の計画から変えた点（理由つき）

## 「ブロッカーなし」の定義
人間への問い合わせゼロではなく、**待たずに進める**こと。
- 判断を「記録から再現できる」「確信度が低い」「戻せない（一方通行）」に分類し、扱いを分ける
- 確信度が低い／戻せない場合は、保守的な既定で進め、判断待ちの質問は非同期キューに積む（作業は止めない）
- 権限を超える判断（予算・外部公開・削除など）は常に人間に回す。この境界も設計対象

## 調査体制
| ID | 担当 | 出力 |
|---|---|---|
| A | 判断の記録スキーマ・ADR | `work/rounds/round-N/A.md` |
| B | マルチソースからの判断抽出 | `B.md` |
| C | 格納形式・ストレージ（MD/JSON/SQL/Vector/Graph）、MCP 連携 | `C.md` |
| D | 検索・抽出・注入タイミング（Hooks/段階的開示） | `D.md` |
| F | 評価（バックテスト）・プライバシー/権限・運用（更新/承認/忘却） | `F.md` |
| E | 批判的レビュー・網羅性監査（独立、A〜D, F の記述だけを読む） | `E-review.md` |

## 追加の観点（E が必ず確認）
- 評価: 過去の判断を伏せて AI に再現させ、一致率を測る方法（保留データ、判断の種類別）
- 判断の分類: 一方通行/やり直し可能、権限レベル、確信度の閾値と退避動作
- 暗黙知: ログに現れない判断の引き出し（インタビュー、反事実質問、逸脱時の理由記録）
- 抽出の誤り: 抽出された「判断」は仮説であり、人間が承認するまで権威を持たない
- 矛盾・陳腐化・汚染: 上司/先輩の矛盾、有効期限・失効、誤った過去判断の引きずり
- プライバシー・法務: 同意、個人情報（日本の個人情報保護法）、各サービス規約、アクセス制御、ログ経由のプロンプトインジェクション
- 既存実装: Claude Code の CLAUDE.md / auto memory / hooks / MCP、本ファクトリーの `harness-lib`、Letta / Zep / Mem0 / GraphRAG 等（実在と現状を確認）
- コストと遅延: 注入トークン量、検索の応答時間

## ループ
1. Phase 1: A, B, C, D, F を並列実行 → `round-N/*.md`
2. Phase 2: E がレビュー（追加リサーチ可）→ `E-review.md`。指摘は番号付きで、各々「再調査要/設計変更要/軽微」に分類
3. Phase 3: 指摘に関係する担当だけ再起動。E の指摘文をそのまま渡す
4. Phase 4: 飽和判定。満たさなければ Phase 2 へ。最大4ラウンド
5. 確定: `docs/research/` に最終成果物を書き、人間が承認

## 終了条件（全て満たす）
1. E の指摘のうち「再調査要/設計変更要」が全て解消済み。各々に実装可能な設計解がある（`99_review_and_iteration_log.md` で対応表を示す）
2. 飽和の測定: 直近ラウンドで E が新規に挙げた主要アーキテクチャ・手法のうち、設計を変える採用案が0件。E は試した検索クエリと、反証を試みた記録を提出する。直近2ラウンド連続で0件、または4ラウンド到達（到達時は未飽和と明記して人間に判断を仰ぐ）
3. 具体性: スキーマ・DDL・抽出プロンプト・Hooks/MCP 設計が実装可能。DDL は SQLite で実行し通ったログを `work/` に残す。プロンプト例は合成データで試した結果を残す
4. 出典: 主要な主張に出典台帳の ID が付き、一次情報で確認した割合が `99` に記載されている
5. 人間の最終承認
